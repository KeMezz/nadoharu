## Context

`post-system` 백엔드가 제공하는 GraphQL API를 앱 사용자 경험으로 연결하기 위해, `apps/web`에 게시물 조회/상세/작성/수정/이미지 업로드 흐름을 추가한다.

현재 프론트엔드는 인증 경계가 있는 게시물 라우트(`/posts`)와 공개 라우트(`/posts/[id]`)를 동시에 만족해야 하며, 레거시 `nadoharu-front`의 화면 톤/인터랙션을 참조해 모바일 우선 UX를 유지해야 한다. 또한 GraphQL 문서 분리, near-operation-file 생성 타입 사용, 라우트 기준 콜로케이션 규칙을 지켜야 한다.

## Goals / Non-Goals

**Goals:**

- 인증 사용자에게 `/posts` 커서 기반 타임라인(초기 로드, 추가 로드, 빈 상태, 오류 상태)을 제공한다.
- 비인증 사용자에게 `/posts` 접근 시 로그인 안내 UX를 제공하고, `/posts/[id]`는 공개 조회를 허용한다.
- 게시물 작성/수정 폼에서 텍스트, subcontent, 이미지 첨부와 제출 상태(로딩/성공/실패/재시도)를 일관되게 처리한다.
- presigned URL 기반 업로드 흐름(파일 검증, 업로드, 실패 복구)을 폼 UX와 통합한다.
- TDD 기준으로 Vitest/Playwright 시나리오를 추가해 회귀를 방지한다.

**Non-Goals:**

- 추천 피드/탭 등 신규 피드 도메인을 도입하지 않는다.
- 고급 에디터 기능(드래그 정렬, 필터, 실시간 공동 편집)은 포함하지 않는다.
- 백엔드 API 계약 자체를 변경하지 않는다(필요 시 별도 change로 분리).
- content 패턴(예: `[카테고리]`) 기반 카테고리 추출/매핑 규칙은 이번 change에 포함하지 않는다.

## Decisions

### 1) 라우트 단위 콜로케이션 구조를 채택한다

- **Decision:** `app/posts`, `app/posts/[id]` 아래 `_components`에 페이지 전용 UI/훅/GraphQL 문서를 배치한다.
- **Rationale:** 현재 저장소의 route-first 규칙과 폼 콜로케이션 규칙을 충족하고, 기능 경계를 URL 기준으로 명확히 유지할 수 있다.
- **Alternatives considered:**
  - 도메인 공용 폴더(`src/features/posts`) 중심 구성: 재사용성은 높지만 라우트별 상태/권한 분기가 분산되어 변경 추적이 어려워짐.

### 2) GraphQL 연동은 실행 모듈 + 인접 `.graphql` 파일로 분리한다

- **Decision:** `*.query.ts`/`*.mutation.ts`는 실행 책임만 갖고, 실제 문서는 인접 `.graphql`로 분리한다. 타입은 near-operation-file 생성 파일(`*.generated.ts`)을 사용한다.
- **Rationale:** 코드 생성 체계와 정합성을 유지하고, 수동 타입 정의로 인한 스키마 드리프트를 방지한다.
- **Alternatives considered:**
  - TS 파일 내 gql 문자열 인라인: 빠르지만 문서 재사용성과 생성 파이프라인 가시성이 떨어짐.

### 3) 인증 경계는 라우트 진입 시점과 데이터 페칭 시점을 분리해 처리한다

- **Decision:** `/posts`는 비인증 시 즉시 로그인 안내 UI를 노출하고, `/posts/[id]`는 공개 조회 쿼리를 기본 사용한다.
- **Rationale:** 사용자에게 권한 정책을 명확히 전달하고, 불필요한 보호 API 호출을 줄여 오류 노이즈를 낮출 수 있다.
- **Alternatives considered:**
  - 모든 라우트에서 서버 응답 후 권한 분기: 구현은 단순하지만 초기 UX 지연과 에러 기반 제어가 늘어남.

### 4) 타임라인은 커서 기반 페이지네이션 + Intersection Observer를 사용한다

- **Decision:** 초기 페이지 로드 후 하단 센티넬 감지 시 다음 커서를 요청하고, 중복 요청을 방지하는 잠금 상태를 둔다.
- **Rationale:** 모바일 환경에서 스크롤 연속성을 확보하고, 페이지 번호 기반보다 API 계약(`cursor`)과 자연스럽게 맞는다.
- **Alternatives considered:**
  - 수동 `더보기` 버튼: 구현 난도는 낮지만 연속 소비 UX가 떨어짐.

### 5) 게시물 폼 로직은 전용 훅으로 분리한다

- **Decision:** `use<PostForm>Form` 패턴으로 검증, 제출, 에러 매핑, 리다이렉트를 UI에서 분리한다.
- **Rationale:** 폼 컴포넌트는 렌더링에 집중하고, 테스트에서 상태 전이를 독립 검증할 수 있다.
- **Alternatives considered:**
  - 컴포넌트 내부 단일 상태 처리: 파일 수는 줄지만 재사용성과 테스트성이 급격히 낮아진다.

### 6) 이미지 업로드는 2단계(메타 등록 → presigned PUT)로 표준화한다

- **Decision:** 파일 선택 시 클라이언트 검증(확장자/용량) 후 presigned URL을 발급받아 업로드하고, 성공 시 게시물 입력 상태와 연결한다.
- **Rationale:** API 보안 경계를 유지하면서도 업로드 실패를 세분화해 재시도 UX를 제공할 수 있다.
- **Alternatives considered:**
  - 서버 프록시 업로드 단일 요청: 단순하지만 서버 부하 증가와 대용량 업로드 확장성 한계가 있다.

### 7) 카테고리 입력 UI는 이번 범위에서 제외한다

- **Decision:** 게시물 작성/수정 UI에서 카테고리 입력 컨트롤을 노출하지 않고, 클라이언트 제출 데이터의 카테고리는 빈 값으로 고정한다.
- **Rationale:** 카테고리 도메인 정책(값 체계, 파싱 규칙, 검증 기준)이 아직 확정되지 않아 임시 UI를 도입하면 이후 마이그레이션 비용이 커진다.
- **Alternatives considered:**
  - 임시 선택형 카테고리 UI 도입: 빠른 노출은 가능하지만 추후 content 패턴 기반 정책과 충돌할 가능성이 높다.

## Risks / Trade-offs

- [무한 스크롤 중복 요청/순서 역전] → 요청 잠금 플래그와 마지막 커서 기준 idempotent 병합 규칙을 둔다.
- [비인증 경계 처리 불일치] → `/posts`와 `/posts/[id]` 권한 시나리오를 Playwright E2E로 고정한다.
- [레거시 디자인 이식 편차] → 핵심 화면(타임라인 카드, 에디터, 로그인 안내) 우선으로 토큰/간격/상태 표현을 매핑한다.
- [업로드 실패 시 사용자 이탈] → 실패 원인별 메시지와 재시도 액션, 업로드 중 취소 UX를 제공한다.
- [GraphQL 타입 생성 누락] → CI/로컬 체크리스트에 `pnpm --filter web graphql:generate` 실행을 포함한다.

## Migration Plan

1. 라우트 뼈대 및 콜로케이션 구조를 추가한다.
2. 타임라인/상세 조회 GraphQL 문서와 실행 모듈을 구현하고 타입을 생성한다.
3. 게시물 작성/수정 폼(카테고리 UI 제외)과 이미지 업로드 흐름을 연결한다.
4. Vitest 단위 테스트(폼 상태 전이, 에러 매핑, 권한 분기)를 작성한다.
5. Playwright E2E(비인증 접근, 무한 스크롤, 공개 상세 조회)를 작성한다.
6. 점진 배포 시 문제가 발생하면 신규 라우트 노출을 비활성화하고 기존 화면으로 롤백한다.

## Open Questions

- 현재 오픈 이슈 없음.
- 확정 사항: 이미지 업로드 정책은 `packages/shared`를 단일 정책 소스로 두고 API가 최종 강제한다.
- 확정 사항: `/posts` 타임라인 정렬은 최신순(`createdAt DESC`, `id DESC`) 고정으로 처리한다.
- 확정 사항: 게시물 수정 권한 실패 UX는 상태 코드 기준으로 구분해 `401`/`403`을 표시한다.
- 확정 사항: 카테고리는 이번 범위에서 UI 미노출 및 빈 값 고정으로 처리하고, content 패턴 기반 지정은 별도 change에서 다룬다.
